# Fork Divergence

This file records changes in `andretakagi/truenas-hailo` that differ from the upstream `scyto/truenas-hailo` baseline. Tracked-version bumps (`.github/tracked-versions.json`) are not listed here — they happen continuously and are visible in `git log` and on the GitHub Releases page.

## Install / Restore Scripts

- **Custom source repository.** `install.sh` accepts `--repo=OWNER/NAME` and the `HAILO_REPO` environment variable, so installs from a fork pull artifacts from the fork's releases instead of upstream. The selected repo is recorded in `${PERSIST_DIR}/.hailo-repo`. On `main`, the default is `andretakagi/truenas-hailo` (not upstream) — the `install.sh` shipped from this fork's releases now requires `hailo.firmware_sha256` in the source repo's `tracked-versions.json` and would hard-fail at firmware verification against upstream's schema. The `upstream-pr/*` branches still default to `scyto/truenas-hailo` for PR submission.
- **Branch-aware preinit error messages.** `hailo-preinit.sh` reads `.hailo-repo` and points kernel-mismatch error output at the source fork's releases page, falling back to upstream if the file is missing.
- **Loud failure on missing HailoRT version.** Install/preinit now exit with a clear error if the HailoRT version cannot be determined, instead of silently proceeding with bad state.
- **Bounded curl downloads.** `install.sh` caps every release/firmware/install-script download with `--max-time`, so a stalled connection fails fast instead of hanging the install indefinitely.
- **`install.sh --check`.** Read-only probe of an existing install: device node, kernel module, sysext file/merge state, persistent config + backup, PREINIT script + middleware registration, kernel-version match, and PREINIT boot result (most recent line from `journalctl -b -t hailo-preinit`). The PREINIT-boot check passes only on the `Done` sentinel, fails on any `ERROR:` line, and warns if the unit hasn't run this boot — so a sysext that the kernel loads but PREINIT silently broke shows up here instead of three days later when Frigate can't reach the device. Each failure includes a one-line hint at the next step. Exits 1 if any check fails. Useful for support reports.
- **`install.sh --dry-run`.** Performs every read/network/validation step (release lookup, sha256 verify, firmware download, squashfs unpack/repack) but skips every command that mutates the running system. Each skipped mutation is logged as `[dry-run] would: <command>` and the run ends with a summary of what would have been installed. Mutually exclusive with `--check`.
- **`/tmp/hailo.raw` self-copy guard.** Passing `install.sh /tmp/hailo.raw` (the path the `--help` examples used to suggest) collides with the installer's staging path: `cp` would refuse and the EXIT-trap cleanup would then `rm -f /tmp/hailo.raw`, deleting the user's input. The script now resolves the realpath of both and refuses with a clear "move/copy and re-run" error rather than risk the data loss.
- **`midclt` lookup refused on transient error.** TrueNAS init-script records aren't keyed by command, so a midclt query that fails mid-install would otherwise fall through to `create` and produce a duplicate registration that `restore.sh`'s first-match cleanup can't fully undo. `install.sh` now distinguishes "not registered" from "lookup error" and aborts on the latter rather than guessing.
- **Firmware sha256 verification.** `install.sh` fetches `hailo.firmware_sha256` from the source repo's `tracked-versions.json` and verifies the downloaded Hailo-8 firmware against it. The Hailo S3 bucket does not publish per-blob `.sha256` files, so without this the installer was downloading and injecting an unauthenticated proprietary blob. Hard-fails on missing/malformed published value or mismatch (with bad-firmware cleanup). Runs unconditionally including under `--dry-run` — a dry-run that skips integrity checks would give false confidence. The producer-side workflow (`check-releases.yml`) records the sha256 in the same auto-bump commit, so the `tracked-versions.json` snapshot used to resolve the HailoRT version is the same snapshot the verification reads from (no TOCTOU window between the two fetches).
- **`scripts/uninstall.sh` wrapper.** Discoverable alias around `restore.sh` (the actual uninstaller, named historically). Ships in the release alongside `restore.sh` so users can `curl … uninstall.sh | sudo bash` without knowing the legacy name. The wrapper handles both the sibling-on-disk case (when both files are downloaded together) and the stdin-piped case (the `curl | bash` path), downloading `restore.sh` to a tmpfile in the latter and cleaning up via EXIT trap.

## Sysext Activation on TrueNAS

- **`systemd-sysext unmerge` before ZFS writes.** `install.sh` and `restore.sh` now `unmerge` the sysext (rather than `refresh`) before unlocking `/usr`, so the overlay does not block the remount. Without this, repeated installs/restores would intermittently fail.
- **PREINIT script bundled in `hailo.raw`.** `scripts/hailo-preinit.sh` ships inside the sysext at `/usr/lib/hailo/hailo-preinit.sh`. `install.sh` extracts it during the existing firmware-injection unsquashfs/mksquashfs cycle and copies it to the persistent pool. Replaces the prior arrangement where `install.sh` carried an ~130-line heredoc copy of the same script, kept in sync by a `check-preinit-sync.sh` lint gate.
- **`/usr` readonly restored on signal in PREINIT.** `hailo-preinit.sh` (and `install.sh`/`restore.sh`) install a `trap restore_usr_readonly EXIT INT TERM` so a SIGINT/SIGTERM (or unexpected error path) between `zfs set readonly=off` and the matching `readonly=on` does not leave `/usr` writable until reboot.
- **Empty-SHA256 defensive reinstall in PREINIT.** If `sha256sum` returns an empty hash for either the installed sysext or the backup (rare: ZFS read error, pool flapping at PREINIT, overlay weirdness), `hailo-preinit.sh` now reinstalls from backup rather than treating two empty strings as a match and silently leaving a possibly-broken sysext active.
- **`hailo-load.service` idempotent + module-path discovery.** The unit now guards on `[ -e /sys/module/hailo_pci ]` so it no-ops when PREINIT already loaded the module (the unit still acts as a backup if PREINIT registration is broken). The mismatch-detection path in `hailo-preinit.sh` selects the sysext's kernel by scanning `/usr/lib/modules/*/extra/hailo_pci.ko`, not by picking the first non-running directory — after multiple TrueNAS upgrades several kernel dirs can coexist.

## Automated Workflows

- **Single check workflow + single state file.** Replaced the two scheduled workflows (`check-truenas-release.yml`, `check-hailo-release.yml`) and the three root-level state files (`version`, `train`, `.hailo-driver-version`) with one workflow (`.github/workflows/check-releases.yml`) and one CI-state file (`.github/tracked-versions.json`). When both upstreams move on the same day, only one consolidated build is dispatched instead of two back-to-back. A `concurrency` block serializes manual dispatches against the scheduled run so they cannot race on the commit/push.
- **Daily schedule.** The unified `Check for New Releases` runs daily at 06:00 UTC instead of weekly.
- **Explicit `GITHUB_TOKEN` permissions.** Scheduled workflows declare `permissions:` blocks so the default read-only token does not block issue/dispatch/push API calls.
- **Branch-aware HailoRT detection.** The check shallow-clones the upstream `hailo8` branch and uses `git tag --merged origin/hailo8` to enumerate candidate tags. The previous `/tags` API + major-version filter could not guarantee a 4.x tag actually lived on `hailo8`.
- **Hailo auto-bump and auto-build.** When a newer hailo8-reachable tag is detected, the workflow commits the bump to `.github/tracked-versions.json` and dispatches `build.yml` directly (the previous flow filed an issue and waited for a human dispatch).
- **TrueNAS ISO availability gate.** The check only bumps the tracked TrueNAS version and dispatches `build.yml` once the matching ISO is published at `download.truenas.com`. Tags in `truenas/scale-build` can land hours or days before the ISO appears.
- **Auto-resolved train name.** The check no longer hardcodes a major.minor filter or the train name. It picks the highest stable scale-build tag, resolves the train name from `download.truenas.com`'s directory listing, and writes both `version` and `train` atomically. When iXsystems rolls a new train (Goldeye → next), the daily check picks it up automatically and surfaces a `::notice::` annotation on the run that does the rollover.
- **Frigate-pin gate on Hailo bumps.** The check caps the candidate version at the `hailo_version` pinned in Frigate's `docker/main/install_hailort.sh` on the `dev` branch. The tracked driver never moves ahead of what Frigate's bundled userspace can talk to. When the gate is actively suppressing a newer Hailo release, the run surfaces a `::notice title=Frigate cap active::` annotation so the operator can see at a glance that there is upstream work waiting on Frigate to bump.
- **`mark_latest` input on `build.yml`.** The scheduled check dispatches with `mark_latest='false'`, so auto-built releases publish without claiming the "Latest" badge. A human still promotes a release to Latest in the GitHub UI after verifying it on Hailo-8 hardware. Manual `workflow_dispatch` invocations default to `mark_latest='true'` to preserve previous behavior.
- **Build runner resolved per-build.** `runs-on:` is no longer pinned to `ubuntu-22.04`. The check invokes `.github/scripts/resolve-runner.sh` to look up TrueNAS's Debian release from its own published build metadata (`GITMANIFEST` → `truenas-build/conf/build.manifest`) and pick a matching Ubuntu runner. When TrueNAS rebases onto a new Debian release, the auto-bump fails loud with `::error::unknown debian_release '<codename>'` and the fix is a one-line `case` arm — no more hand-tracking which Ubuntu pairs with which TrueNAS.
- **Auto-synced `workflow_dispatch` defaults.** Each auto-bump commit also rewrites `build.yml`'s `workflow_dispatch` defaults via `.github/scripts/sync-build-defaults.sh`, so a manual "Run workflow" in the Actions UI always pre-fills the latest tracked combination (TrueNAS version, train, HailoRT driver, runner). The substitution is structurally validated and fails loud if `build.yml`'s shape drifts.
- **Lint workflow with shellcheck + actionlint.** `.github/workflows/lint.yml` runs `shellcheck --severity=warning` against all shipped shell scripts (`scripts/*.sh`, `.github/scripts/*.sh`) and runs [`actionlint`](https://github.com/rhysd/actionlint) against every workflow YAML. `actionlint` is wired with `-shellcheck "shellcheck --severity=warning"` so inline `run:` blocks are linted at the same severity as the standalone job, catching shell issues in `build.yml` that the file-level shellcheck job doesn't see.
- **Strict ELF check on HailoRT build artifacts.** `build.yml` now exits with `::error::` if `libhailort.so` or `hailortcli` are missing or aren't real ELF binaries (the cmake build directory mixes wrapper scripts in alongside the real binaries — picking up a wrapper used to silently produce a broken sysext). Candidates are listed on failure for diagnosis.
- **Build-time smoke test on `hailo.raw`.** Before publishing the release, `build.yml` unsquashes the freshly-built sysext and asserts: required files exist at expected paths, `libhailort.so` and `hailortcli` are real ELFs, and `hailo_pci.ko`'s vermagic matches the kernel the sysext is meant for (caught with `modinfo`). Distinct gate from the assembly-time ELF check — the smoke test catches drift in `mksquashfs` flags, missing-file regressions, and kernel-header mismatches that would slip past the assembly check. Failures use `::error title=smoke-test::` annotations.
- **Richer release-notes body.** `build.yml` now generates the release body from a heredoc that includes the real kernel version (parsed from the bundled `hailo_pci.ko` vermagic), the Ubuntu runner image used, the build commit SHA, and a link to the exact Frigate `install_hailort.sh` (dev branch) the tracked driver was gated against. Replaces the prior static-template body that didn't surface any of the per-build provenance.
- **Firmware sha256 captured on Hailo bumps.** When `check-releases.yml` bumps `hailo.driver`, it also fetches the new firmware blob from the Hailo S3 bucket once, computes the sha256, and writes it to `hailo.firmware_sha256` in the same commit. Hard-fails the bump on fetch error, empty body, or malformed sha256 — better to leave the daily check stuck for 24 h than to commit a wrong sha that would brick every subsequent install. Curl timeout is `--max-time 300` to match the consumer-side install.sh's tolerance.
- **`tracked-versions.json` schema validates `hailo.firmware_sha256`.** `.github/scripts/validate-tracked-versions.sh` now requires `hailo.firmware_sha256` and rejects any value that isn't a 64-char lowercase-hex string. Catches hand-edits and bot bugs at lint time, before they reach an installer.
- **Dependabot for `github-actions`.** `.github/dependabot.yml` opens weekly PRs to bump action major versions, so floating `@v4`/`@v7` references don't drift silently.
- **`tracked-versions.json` shape gate.** `.github/scripts/validate-tracked-versions.sh` runs in `lint.yml` and fails the build if `.github/tracked-versions.json` is malformed JSON, missing `truenas.{version,train}` / `hailo.driver`, has an empty train, or has a version string that doesn't match `X.Y.Z[.W]`. Catches hand-edits before they break a scheduled `check-releases` run.

## Documentation

- README and install/restore docs point at `andretakagi/truenas-hailo` releases instead of upstream.
- README credits `scyto/truenas-hailo` as the upstream project.
- `docs/troubleshooting.md` documents the kernel-mismatch recovery flow that the PREINIT script reports after a TrueNAS upgrade. README and install docs cross-link to it.
- README has a top-level `## Compatibility` section documenting that this fork is Hailo-8/8L only — the Hailo-10/15 driver lives on a different upstream branch (`hailo10`/`hailo15`) and is not in scope here. Replaces a duplicated one-line "Important Notes" mention that was easy to miss.

## Known constraints

- **HailoRT requires exact-match between kernel driver and userspace library.** The library checks the driver version on init and refuses to load with `HAILO_INVALID_DRIVER_VERSION(76)` on any mismatch — it is not "same minor" or "newer driver tolerates older lib", it is exact equality. The sysext ships the kernel module; Frigate's container ships its own bundled `libhailort` and Python wheel via `docker/main/install_hailort.sh`. Both must agree.
- **Frigate is the canonical consumer.** Tracked driver version is therefore gated by Frigate's pin (currently `4.21.0` on both stable `v0.17.1` and `dev`). When Frigate bumps `hailo_version` in its install script, the next scheduled Hailo check on this fork picks up the new ceiling automatically.
